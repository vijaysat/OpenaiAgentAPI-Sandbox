1. `scripts/terraform_rollout.py plan --revision N --review-id ...` uploads only Terraform sources and the provider lock to OCI Resource Manager. Inspect its retained logs. 2. `scripts/rollout.py adopt-foundation --journal portfolio-advisor/deploy/private/vault-bootstrap.json --review-id ...` preserves the existing sandbox project while moving it to the dedicated compartment. 3. `scripts/setup_hosted_database.py prepare --review-id ...` obtains the service CA and seeds the database URL directly in Vault. With the temporary Bastion enabled, run `session`, wait for ACTIVE, then `bootstrap`. The runtime role has no superuser, role-creation, database-creation or replication privileges. 4. Apply runtime IAM with the exact application ID and five secret references. Generate reference-only environment configuration with `rollout.py environment --openai-project <actual-project>`, then `configure`. Local root `.env` retains the development security-token profile; the hosted app uses resource principals. `PORT` is reserved by OCI and must not be added to hosted environment configuration.
5. `scripts/build_hosted_image.py publish --review-id ...` exports only allowlisted application sources to the dedicated private OCI repository. It commits inside a private temporary checkout, never in the working repository. `start` builds the pinned source commit on amd64 and installs public OCI SDK 2.189.0 from the hashed requirements lock; `status` verifies successful delivery and obtains the registry digest.
6. `rollout.py deploy --container-uri <dedicated-registry/repository> --tag <unique-source-tag> --digest <verified-digest>` creates the initial deployment with the real image. Retain its ID immediately and add it to Terraform `runtime_ids` alongside the application ID. Live evidence established that OCI pulls the image as the application principal but reads Vault inside the container as the **deployment principal**. Apply that exact-identity correction; never replace it with a compartment-wide membership rule. A first deployment can fail startup before this permission propagates. Reconcile the failed creation work request, correct access, then use `deploy ... --retry-failed` to activate the same registered artifact. This guarded retry requires a terminal failed work request and never adds a duplicate artifact. If a later, separately diagnosed failure needs another activation, use `--activation-attempt 2` (then 3, etc.); the preceding attempt must have a retained FAILED work request, and each attempt is journaled independently. `status` must report ACTIVE and a matching artifact/tag/digest before calling deployment complete.
7. Run `scripts/verify_hosted_application.py` to check the active image, prefixed UI/assets, API/database/worker health, anonymous access denial, and PKCE sign-in redirect. It saves a credential-free evidence report. Complete Oracle login in the browser separately; this smoke check does not certify a successful SSO callback or model analysis.

All `rollout.py` commands above require `--journal portfolio-advisor/deploy/private/vault-bootstrap.json`; its default is intended for a new independent rollout. All scripts live under `portfolio-advisor/scripts/` and use `portfolio-advisor/.venv/bin/python`.

## Acceptance evidence

Keep local tests, cloud build validation, live infrastructure, authenticated UI behavior, and a completed model analysis separate. The container build verifies its non-root UID, API imports, PostgreSQL driver, public CA and Bash transport. Hosted checks must additionally verify Vault access, database persistence, SSO callback, authenticated API ownership, worker activity and an OCI-backed Luna analysis with matching command/root-turn/artifact evidence.

Runtime policy statements use `request.principal.id` conditions for the exact `runtime_ids`. Each Vault statement also requires an exact `target.secret.id`; object and registry statements retain their exact bucket/repository conditions. This provides the same identity/resource boundary without depending on dynamic-group membership refresh. The application principal additionally has `read container-scan-results` in the dedicated compartment, required by artifact registration with vulnerability scanning enabled. A metadata-only audit projection identified the application principal on `ListContainerScanResults`, despite the provider error naming the deployment. This read-only rule does not permit modifying scan configuration. See [Oracle scanning IAM policies](https://docs.oracle.com/iaas/scanning/using/iam-policies.htm). The dynamic group remains as an inventory of the two owned runtime identities. Oracle documents approximately an hour for [matching-rule changes](https://docs.oracle.com/en-us/iaas/Content/Identity/dynamicgroups/Updating_Dynamic_Groups.htm) and demonstrates [exact-principal resource access](https://docs.oracle.com/en-us/iaas/database-tools/doc/set-mcp-server.html). No runtime permission applies to an unconstrained `any-user`.

OCI's gateway strips the invoke prefix and rewrites Host. Hosted middleware restores the configured prefix and canonical HTTPS origin before the existing route/authentication stack. It ignores caller-provided forwarding headers, while direct health probes with the full prefix also work. The frontend, SSO callback and cookie paths retain the public prefix. Local mode keeps its original host validation and routing. The hosted container must be reached through OCI's gateway; it is not configured as a separate public web server.

Do not reuse the expired setup sandbox as live proof. No success claim follows from an accepted build/deployment request alone. The dedicated sandbox project retains the separately authorized ALLOW_ALL policy; the original restricted DNS behavior is still unverified.

## Recovery

An unconfirmed journal operation stops replay. Inspect its work request, resource tags and current state before reconciliation. Run mutations sequentially; journal writes use locking and reject stale process snapshots. Corrected Terraform plans retain existing resources and state. Cloud source publication rejects a changed branch; image publication rejects an existing tag. Restore the previous recorded hosted artifact for application rollback, then verify its digest. Keep PostgreSQL/Vault and reports intact unless deletion is explicitly requested. Remove temporary setup access after use.

Use a new Terraform revision for each configuration transition, including returning to earlier inputs. Source-update journal entries include both the content digest and revision so removing a temporary grant updates the live stack even when those disabled inputs were used before. Repeating the same revision remains idempotent. A regression test exercises disabled → enabled → disabled and verifies that replay does not submit another update or plan.

Use `scripts/cloud_diagnostics.py build` or `runtime` for service messages. These commands scope searches to the exact dedicated service log, reject Audit records, select only message fields, and redact token/password patterns. Do not dump full OCI audit records: their request headers may contain temporary delegated credentials.

If runtime identity is uncertain, a separate narrowly filtered audit query may project only `datetime`, `data.identity.principalId`, `data.response.status`, and `data.eventName` **on the server**. Restrict the filter to the exact owned application/deployment IDs and deployment time window. Field names are case-sensitive. Never select full events, requests, headers or payloads. The retained startup diagnosis used this metadata-only projection to establish deployment-principal `GetSecretBundle` failures.

The approved fifth build published successfully. The temporary registry-management statement was then removed by Terraform and its absence independently verified; the repository remains private. See [the execution record](REGISTRY_UNBLOCK_REVIEW.md). `registry_publish_until` is empty again and must not be enabled or renewed without another explicit approval; the general rollout review ID does not authorize that extra permission.

## Public SDK build migration

The build no longer uploads or downloads a private SDK wheel. Only `APP_BASE_PATH` and `IMAGE_TAG` are build arguments; update the dedicated pipeline configuration before the next authorized cloud build. The `upload-wheel` action has been removed. Existing build buckets and journal entries are retained; old `build_wheel` and `wheel_upload_intent` fields are ignored. This source change does not deploy or alter existing cloud resources. Source exports and runtime images include the repository MIT license.

The build validates one nonempty filesystem layer using `scripts/check_image_layers.py`.
Docker may additionally emit its canonical empty tar layer for `WORKDIR`; this is
accepted by digest. Additional filesystem layers are rejected so superseded base
filesystems cannot remain in the published image.
